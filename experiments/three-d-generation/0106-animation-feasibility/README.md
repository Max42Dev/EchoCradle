# 0106 — Mesh animation generation feasibility

**Status:** done (paper/README study + a Blender API spike — no generative motion model run)
**Date:** 2026-09-29
**Author:** agent

## Question

For a mesh that was just generated by the image-to-3D stage, should animation be
**(i) fully generated locally**, **(ii) template rig + auto-skin + retargeted stock
clips**, or **(iii) authored offline** — given the L4 24 GB / ~34 GB-disk budget and
a hard requirement that the result imports into Unity?

## Hypothesis

Fully generated rigs+animation are not yet practical locally; a template rig with
auto-skinning plus retargeted stock clips is the realistic path.

**Outcome: hypothesis confirmed, with a refinement.** (ii) is the answer, and a
*middle* path is now genuinely available: **learned auto-rigging (UniRig, MIT,
≥8 GB VRAM)** instead of hand-placed template skeletons. But **(iii) authored
offline** remains the only way to get *game-quality* monsters, and motion
generation is blocked on a **licence** issue (SMPL), not just on hardware.

## Setup

- **OS:** Windows Server 2022 (x64).
- **Hardware:** NVIDIA L4 24 GB, 16 GB RAM, ~34 GB free disk.
- **Runtime:** Blender **5.2.1 LTS** (`C:\Program Files\Blender Foundation\Blender 5.2`),
  headless (`--background --python`). Rigify ships as a core add-on and is present.
- **Models / tools considered:**
  - **UniRig** (learned auto-rig + skinning, MIT, ≥8 GB VRAM, ~10.9 GB repo but
    ~4.2 GB usable) — https://github.com/VAST-AI-Research/UniRig
  - **Rigify** (Blender core, generatively shared human metarig + control rig)
  - **Blender auto-skinning** (`parent_set(type="ARMATURE_AUTO")`, bone heat)
  - **MDM** (text→motion diffusion, MIT code, ~0.4 s/sample) — https://github.com/GuyTevet/motion-diffusion-model
  - **MotionGPT** (LLM-style motion-language, MIT code) — https://github.com/OpenMotionLab/MotionGPT
  - **AnimateDiff / video-to-motion** (2D video models; not a mesh-space source)

## Per-option conclusion

### (i) Fully generated motion — `inconclusive` / `rejected` for v1
Text-to-motion models (**MDM**, **MotionGPT**) run locally and cheaply (MDM:
~0.4 s per sample at 50 diffusion steps on a single CUDA GPU). **But** they do not
solve *our* problem, for three reasons:

1. **They output SMPL parameter sequences, not mesh animation.** SMPL is a fixed
   human body model; every output is a human body. A generated monster, a prop, a
   quadruped or a snake cannot be animated by them. You still need a rig, and the
   result must be **retargeted** onto it.
2. **SMPL is licence-gated.** The *code* is MIT, but MDM/MotionGPT depend on the
   **SMPL/SMPL-X body models**, which require a registration and are **not
   redistributable** — a poor fit for a shipped game (Golden Rule: local, and the
   project cares about licences for assets).
3. **Fixed skeleton topology.** Retargeting SMPL joints to an arbitrary predicted
   skeleton is itself a non-trivial step and loses fidelity for non-humanoids.

**Video models (AnimateDiff, video-to-motion)** generate *pixels*, not rig
animation — they cannot drive a mesh, and at 10–16 GB VRAM plus a large checkpoint
they are the worst fit on this box. `rejected`.

**Verdict:** motion *generation* is feasible locally for humanoids, but it is a
"nice to have", not the pipeline. Defer it.

### (ii) Auto-rig + auto-skin + retargeted stock clips — **recommended**
This is the answer. Three sub-parts, all verified:

- **UniRig** predicts a *topologically valid skeleton* for arbitrary meshes
  (humans, animals, objects) from geometry alone, then predicts per-vertex skin
  weights. It is **MIT-licensed**, needs **≥8 GB VRAM**, and exports/imports
  `.obj`, `.fbx`, `.glb`, `.vrm`. Usable subset is ~4.2 GB (skeleton + skin
  checkpoints), comfortably inside the disk budget. This removes the biggest
  weakness of the template approach (a fixed skeleton forcing every asset into one
  shape).
  - **Caveat:** the currently released checkpoints are trained on
    Articulation-XL2.0; the authors say quality is **best when the skeleton is
    refined before skinning**, and that a bad skeleton degrades skinning
    "significantly". So it is a *draft* rig, not a final one.
- **Rigify** (Blender core, zero disk/VRAM) is the fallback for humanoids: place the
  metarig, align it to the generated mesh, `pose.rigify_generate()`, then
  `ARMATURE_AUTO` skinning. Fully scriptable except the alignment.
- **Auto-skinning** (`parent_set(type="ARMATURE_AUTO")`, bone-heat) is the glue
  step and works well on clean, manifold meshes — but generated meshes are often
  non-manifold, so **weight cleanup is mandatory** (`vertex_group_clean`,
  `vertex_group_limit_total`, then verify ≤4 influences).

### (iii) Authored offline — **recommended for hero assets**
For monsters and featured NPCs, hand-authored rigs + animation remain the only way
to reach game quality. Generated meshes can *still* be used: retopologise, hand-rig,
then reuse the same stock-clip library. This is the "authoring-time" path the
original hypothesis predicted, and it stays.

### Disk/VRAM reality check for animation on this box
- UniRig usable ≈ **4.2 GB** (the 10.9 GB repo includes a 4.6 GB dataset we do not
  need) — fits alongside the ~5–17 GB from experiment 0103.
- MDM/MotionGPT checkpoints are **1–3 GB** but drag in SMPL data. Not recommended.
- AnimateDiff-class video models are **several GB** and out of scope.
- **No animation model needs to be resident at the same time as the 3D model** —
  animation is a post-step on an existing mesh, so it never competes for VRAM with
  the shape generator.

## Conclusion

`promising` — the question is answered.

**Recommended animation approach: a hybrid, in this order.**

1. **Template rig + retarget (primary, covers most assets).**
   Rigify human metarig (or a small set of quadruped/prop metarigs) →
   auto-skin (`ARMATURE_AUTO`) → weight cleanup → **retarget a small stock clip
   library** (idle / walk / attack / hit / death) → export GLB with the clips
   stashed on NLA tracks. Zero models, zero VRAM, fully scriptable in Blender.
2. **UniRig for non-human/odd topology** (MIT, ≥8 GB VRAM, ~4.2 GB disk) when the
   asset isn't a biped and a template rig would distort it. Treat its output as a
   *draft rig* to be reviewed.
3. **Authored offline for hero monsters** — the generated mesh is the starting
   point, not the finished asset.
4. **Do NOT generate motion locally for v1.** Text-to-motion is feasible in
   isolation but outputs SMPL-only humans and is blocked by SMPL licensing. Revisit
   only for an all-humanoid roster and only if a licence-clean body model is found.

**Blockers / risks:**
- **SMPL licence** is the hard blocker for any fully-generated human motion pipeline
  (MDM/MotionGPT). The *code* being MIT does not make the *outputs* safe.
- Generated meshes are frequently **non-manifold / unweightable**; auto-skin can
  silently produce unweighted vertices. Hence `src/blender_rig_check.py` is a
  required gate, not a nicety.
- UniRig's released checkpoints are **not** the paper's full-quality models
  (skeleton+skinning trained on Rig-XL/VRoid are still "planned"); expect to
  refine skeletons.
- Retargeting quality depends on a **consistent bone naming/rest-pose convention**;
  this must be fixed as a project standard before clips are authored.
- The clips themselves are an **authoring asset** — generate/model them once,
  offline, and ship them; they are tiny next to any generative model.
