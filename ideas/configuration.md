## Summary

**All game information lives in config files (typed JSON).** Character backgrounds,
enemy stats, shops, items, level setup, player stats, player history, save files — all of
it. Unity objects are **derived** from configs: they are built at load time, used, and
thrown away. They are never the place where information lives.

```
config (JSON)  ──►  Unity object / subsystem  ──►  used, then discarded
   the source            a view of it               never persisted
```

This inverts the usual Unity habit. A `MonoBehaviour` or `ScriptableObject` in the scene
is not the NPC's data; it is a *temporary thing constructed from* the NPC's config so the
engine has something to run. If you delete every GameObject, nothing is lost — the configs
still describe the whole game, and the objects rebuild themselves.

The practical reason: configs are text. They can be reviewed, diffed, version-controlled,
generated by an LLM, validated against a schema, and hand-edited. Unity objects can do
none of those things. Anything that must be *known* is a config; anything that must
*exist at runtime* is a Unity object built from a config.

---

## The rule

> **Configs hold information. Unity objects hold nothing that isn't in a config.**

Corollaries:

- If a value matters after a restart, it belongs in a config (content or save). Not in a
  component field, not in a static, not in a scene.
- Unity objects are **disposable**. Rebuilding them from configs must reproduce the game
  state. That is the test of whether the split is right.
- A Unity object may hold *runtime-only* state (cached transforms, current animation,
  a physics handle) — that's fine, because it is reconstructed, not saved.

## What goes in configs

| Config | Contains |
| --- | --- |
| `npc` | id, name, background/appearance text, stats, faction, behaviour id, dialogue id |
| `enemy` | id, name, base stats, damage types, loot table id, AI profile id |
| `behaviour` | AI parameters: aggro range, patrol pattern, combat style, schedules |
| `shop` | id, stock list (item ids + price modifiers), restock rule |
| `item` | id, name, description, stats, icon ref, value |
| `loot` | id, weighted entries, drop rules |
| `level` | id, seed, room/encounter layout, spawn table ids, connections |
| `player` / `archetype` | base stats, growth curves, starting kit |
| `dialogue` | id, lines, conditions, LLM prompt hints |
| `save` | player state, history, world deltas, seed |

Anything in that list that is currently a `ScriptableObject`, a prefab, or a scene object
becomes a config.

---

## What stays a Unity object

Only these, and always as things *built from* configs:

| Unity thing | Why it can't be the source of truth |
| --- | --- |
| `GameObject` / scene | Spatial, transient; rebuilt from a level config. |
| `MonoBehaviour` | It's a behaviour runner, not a data container. Reads its config. |
| `ScriptableObject` | Allowed only as a **thin adapter** so a config shows up in the inspector — it wraps a loaded config, it does not own data. |
| `Sprite`, `AudioClip`, `Material`, `Prefab` | Binary assets. Configs reference them **by id**, never embed them. |

The last row is the whole story of the "not 1:1" point: a config says `"icon":
"icon.iron-sword"`, and something resolves that id to a `Sprite` at build time. The config
does not try to be the sprite.

## Configs are typed, so they transfer cleanly

Configs are defined by C# types, so there is one definition per concept and a direct
mapping in both directions:

- **Code reads a config** → into a C# object it can work with.
- **Code writes a config** → from that same object.

This is what makes "object changes → file changes" possible without hand-written
conversion code: the type *is* the mapping.

### Practical choices

| Choice | Why |
| --- | --- |
| **Newtonsoft.Json** (`com.unity.nuget.newtonsoft-json`) | Unity's `JsonUtility` can't do dictionaries, can't tell `null` from missing, and can't express a list of mixed types. All three appear in this data. |
| **Enums as strings** | Readable, and reordering the enum doesn't silently change meaning. |
| **Stable field order** | So a rewritten file is a clean diff, not a reshuffle. |
| **`schemaVersion` per config** | So a config written today still loads after the type changes. |
| **Plain C# classes**, no `MonoBehaviour` | So the model can be tested, generated, and validated without Unity running. |

### Referencing Unity assets

A config stores the **identity** of an asset, not the asset:

```json
{ "id": "item.iron-sword", "name": "Iron Sword", "icon": "icon.iron-sword" }
```

`"icon.iron-sword"` resolves to a `Sprite` through an id → asset lookup (Addressables or
an id table). If the asset is missing, a placeholder is used. This keeps configs purely
text and keeps binary assets swappable.

## Where things are stored

```
# Content — describes the game, committed to git
Assets/Data/
  npcs/npc.blacksmith.jora.json
  enemies/enemy.bandit.json
  behaviours/behaviour.bandit.json
  shops/shop.blacksmith.jora.json
  items/item.iron-sword.json
  levels/region-01.json
  dialogue/dialogue.blacksmith.jora.json

# Generated content — LLM/tool output, validated before use
Assets/Data/Generated/...

# Runtime state — per player, never committed, never shipped
%persistentDataPath%/Saves/<slot>/
  state.json      # current player + world state
  history.ndjson  # append-only event log (player history)
  world.json      # only the deltas the player caused
  meta.json       # slot name, playtime, timestamps, seed
```

One entity per file where practical: small files diff and merge cleanly, and rewriting one
NPC doesn't touch anything else.

---

## References and validation

- **Every entity has a readable string id** (`npc.blacksmith.jora`).
- **References are always by id** — never by array index, file path, or Unity instance id.
- **A validator checks them.** Walk all configs, resolve every reference, fail the build
  on a dangling id. Cheap to write, catches the most common content mistake.
- **LLM output is validated before it is used.** Generated configs land in `Generated/`,
  are checked against the schema, and only then are they treated as content.

## Saving

Because configs are typed, saving is just writing the current state out as a config. There
is no separate save format.

- **Content configs** change rarely, are edited by tools/designers/LLMs, and are committed.
- **Save configs** change constantly during play and live on the player's machine.
- A save stores **state + ids + seed**, not a copy of the content, so content updates don't
  invalidate old saves.
- Storing the **seed** makes generated content (levels, loot) reproducible.
- Write atomically (temp file, then replace) so a crash can't leave a half-written file.
